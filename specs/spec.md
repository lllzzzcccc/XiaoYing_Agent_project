# 内容任务规划 Agent 规格

- 阶段：Specify
- 来源：`小影科技2027校招-AI Agent笔试题 · 卷面.html` 第 2 题及试卷通用交付规范
- 技术栈约束：Node.js + TypeScript + Pi Agent Runtime
- 本文仅定义需求、业务规则和验收条件，不规定具体实现。

## 1. 约定与优先级

- “必须”表示交付验收的强制要求，“应”表示无正当理由不得偏离的要求，“可”表示可选能力。
- P0：核心交付或原题明确要求的验收项；P1：原题明确的加分项或补充质量要求。
- 状态术语：
  - **已完成**：当前方案满足预算和截止时间，所有必需步骤成功，并且方案保存成功。
  - **未完成**：因输入不足、约束不可满足、工具失败、达到执行上限或其他原因，未达到“已完成”。未完成不等于所有步骤都失败。
  - **重复执行**：使用相同 `request_id` 和相同输入再次发起已处理过的请求；系统返回原结果并标记 `duplicate=true`。
  - **请求冲突**：使用已存在的 `request_id` 但输入内容不同；系统必须拒绝该请求，不得覆盖原结果。
- 本规格不要求披露模型内部思维过程；运行记录只保留可审计的简要决策依据。

## 2. 用户、目标与成功标准

- USR-001（P0）：目标用户为需要制定内容活动方案的运营人员。
- USR-002（P0）：系统必须帮助用户在给定预算与截止时间内形成并保存一份内容活动方案。
- USR-003（P0）：系统必须让用户能够核对任务计划、步骤依赖、各步骤实际状态、工具结果、费用合计及最终保存结果或未完成原因。
- USR-004（P0）：系统必须体现模型依据工具观察结果进行动态调整，而不是仅按固定顺序调用全部工具。
- USR-005（P0）：成功标准须由实际运行记录和可执行验证材料证明，不能仅以预设日志、截图或视频代替。

## 3. 范围

### 3.1 范围内

- SCP-001（P0）：围绕单个内容活动主题进行素材检索、脚本生成、成本估算、方案调整与方案保存。
- SCP-002（P0）：使用合成素材以及工具费用与耗时表，评估候选方案的预算和时间可行性。
- SCP-003（P0）：处理正常完成、输入缺失或非法、无素材、工具失败、保存失败、预算超限、无可行方案、部分成功、重复执行、请求冲突和执行上限。
- SCP-004（P0）：保存任务状态与已成功步骤的结果，使重规划或停止后仍能核对已发生的工作。
- SCP-005（P0）：提供真实模型决策证据；模型不可用时的离线 Mock 仅作为补充流程验证入口。
- SCP-006（P1）：失败步骤续跑属于可选加分能力，不作为核心交付的阻断项。
- SCP-007（P0）：使用本地 JSON 保存方案及重复执行判定所需状态，并满足跨进程持久化；不因此扩展为生产级持久化系统。

### 3.2 范围外或非必需

- OUTS-001：图形界面、线上部署、多 Agent 和生产级 Runtime 均不是必需交付。
- OUTS-002：不要求接入真实发布、支付、采购或外部内容平台；方案保存使用本地 JSON。
- OUTS-003：不要求重新实现 Pi Agent Runtime 本身。
- OUTS-004：不提交真实密钥、隐私数据或模型内部思维过程。
- OUTS-005：本阶段不设计内部模块、数据 Schema、工具实现或具体模型供应商；模型供应商保持为配置项。
- OUTS-006：不引入生产级数据库、分布式协调、外部持久化服务或其他外部业务服务。

## 4. 输入、资料与工具能力

- IN-001（P0）：用户输入必须为 JSON，包含必填 `request_id`、主题、预算和截止时间。
- IN-002（P0）：系统必须使用可核对的合成素材、工具费用与耗时资料，不得以凭空编造的费用、耗时或素材结果替代工具观察。
- IN-003（P0）：主题必须为非空字符串，预算必须为非负数，截止时间必须是包含时区的合法 ISO-8601 时间。缺失时必须指出缺失项并请求补充；非法输入必须明确拒绝；任务保持未完成，不得自行猜测、修正或保存为完成方案。
- IN-004（P0）：系统必须提供以下四类业务工具能力：
  - 素材检索；
  - 脚本生成；
  - 成本估算；
  - 方案保存。
- IN-005（P0）：工具可以使用本地函数或 Mock，但其返回必须能被运行记录和最终步骤状态准确反映。
- IN-006（P0）：素材检索无结果时，模型必须能够调整查询并再次检索；调整后仍无可用素材时，必须返回未完成及素材不足原因，不得编造素材或保存完成方案。

## 5. 输出与可审计信息

- OUT-001（P0）：交付结果必须包含任务计划，并能识别各步骤及步骤之间的依赖关系。
- OUT-002（P0）：交付结果必须包含每个已规划步骤的实际状态，至少能区分成功、失败以及未成功完成的状态。
- OUT-003（P0）：交付结果必须包含已执行工具的结果或结果摘要；失败与部分成功不得被省略或改写成成功。
- OUT-004（P0）：交付结果必须包含当前选定方案的费用合计，且能追溯到成本估算结果；历史估算必须保留展示，但不得叠加进最终合计。
- OUT-005（P0）：已完成时必须返回本地 JSON 已保存方案或可核对的保存引用，且保存内容必须可独立读取；未完成时必须返回明确原因。
- OUT-006（P0）：因预算不足而未完成时，未完成原因必须包含预算缺口；预算和时间同时不可行时，两项原因都必须返回；因其他约束未完成时，必须说明对应约束或失败环节。
- OUT-007（P0）：发生重规划、失败或部分成功时，最终可见结果必须保留仍有效的已成功步骤结果。
- OUT-008（P0）：运行记录必须包含步骤、工具参数、工具返回摘要、后续动作及简要决策依据。
- OUT-009（P0）：重复请求必须返回原结果并标记 `duplicate=true`；同 `request_id` 不同输入必须返回明确冲突，不得返回伪造的新成功结果。
- OUT-010（P0）：本地 JSON 保存内容必须包含原始输入、当前方案、素材引用、脚本、费用、耗时和保存时间；相同请求及相同方案视为等价。

## 6. 核心功能需求

- FR-001（P0）：系统必须根据主题检索可用合成素材，并将检索观察用于后续计划；无结果时必须允许模型调整查询，仍无结果则按 IN-006 结束。
- FR-002（P0）：系统必须基于主题和可用素材形成内容活动方案及脚本相关结果。
- FR-003（P0）：系统必须对当前候选方案进行成本估算，并结合工具费用与耗时资料判断是否满足预算和截止时间。
- FR-004（P0）：系统必须按步骤依赖执行或调整计划，不得把前置失败后的依赖步骤当作已成功完成。
- FR-005（P0）：只有在当前方案满足约束且必需步骤成功时，系统才允许请求保存方案；保存结果必须再次据实核对，保存内容必须符合 OUT-010。
- FR-006（P0）：观察到成本超限、工具错误或部分成功时，模型必须能够选择调整计划、采用替代方案或停止，而不是无条件沿原计划继续。
- FR-007（P0）：选择替代方案后，系统必须重新估算当前方案，并在估算满足约束后再决定是否保存。
- FR-008（P0）：无可行方案或无法继续时，系统必须明确结束为未完成，并说明原因；预算不可满足时还必须给出缺口，多项约束不可满足时必须返回全部对应原因。
- FR-009（P0）：系统必须使用 `request_id` 识别请求，并跨进程持久化重复判定所需状态；相同 ID 和相同输入必须返回原结果并标记 `duplicate=true`，不得重复保存；相同 ID 不同输入必须报冲突且不得覆盖原结果。
- FR-010（P0）：系统必须设置执行步数或工具调用次数上限；达到上限时必须停止并返回明确的未完成状态。
- FR-011（P1）：若提供失败步骤续跑，续跑必须保留仍有效的成功结果，只重试失败、未执行或已失效的步骤，不得把续跑前的失败历史改写为成功。

## 7. 业务规则

- BR-001（P0）：费用使用模拟单位，最终保存方案的当前方案费用合计不得超过用户预算。
- BR-002（P0）：从任务开始时间起算，将方案各步骤耗时串行求和得到预计完成时间；预计完成时间早于或等于截止时间均为可行，晚于截止时间则不可行。
- BR-003（P0）：最终合计只计算当前选定方案；历史估算保留展示但不叠加，替代方案被采用后不得沿用旧方案费用，重试不额外计费。
- BR-004（P0）：不得擅自降低、提高或以其他方式改变用户给定的预算、截止时间和主题来制造可行结果；需要变更时必须明确请求用户确认。
- BR-005（P0）：任何失败工具步骤都不得记为成功，任何保存失败都不得声称方案已保存或任务已完成。
- BR-006（P0）：只有依赖条件满足的步骤才能被视为可执行；跳过、未执行、失败和被阻断的步骤必须与成功步骤区分。
- BR-007（P0）：重规划或后续失败不得清除仍有效的成功结果；若原计划变化使既有结果失效，必须明确标识，不得盲目复用。
- BR-008（P0）：部分成功不等于整体完成；最终状态必须由全部必需步骤和保存结果共同决定。
- BR-009（P0）：重复请求必须返回原结果并标记 `duplicate=true`，且不得产生重复保存副作用；相同请求及相同方案视为等价，跨进程重启后该规则仍然有效。
- BR-010（P0）：工具返回、估算结果和保存结果必须据实呈现，不得使用预设决策日志冒充真实观察。
- BR-011（P0）：自动重试不能替代模型依据观察作出后续决策，不能掩盖此前失败记录，也不得增加费用。
- BR-012（P0）：相同 `request_id` 携带不同输入时必须返回冲突，不得覆盖原请求、原结果或原保存方案，也不得产生新的方案保存副作用。
- BR-013（P0）：预算缺口为最低费用候选方案的费用减去预算，且最小为 0；预算与时间同时不可行时，不得只返回其中一项原因。

## 8. 动态决策与执行边界

- DYN-001（P0）：至少一条真实运行路径必须完整体现“模型选择动作 → 执行工具 → 观察结果 → 模型调整下一步或结束”的循环。
- DYN-002（P0）：允许使用预设流程作为执行骨架，但仅有固定条件分支、自动重试或预设决策日志，不满足动态决策要求。
- DYN-003（P0）：模型必须根据成本超限、工具错误或部分成功中的实际观察调整计划、选择替代方案或停止；不同工具结果应能导致不同的后续动作。
- DYN-004（P0）：必须提交至少两条执行路径的运行记录，体现模型根据不同工具结果调整动作。两条路径可由成本变化和工具结果变化等场景形成，但不得只是复制同一条预设路径。
- DYN-005（P0）：执行上限必须实际约束模型步骤或工具调用，达到上限后的状态必须是未完成，不得宣称完成或继续无界执行。
- DYN-006（P0）：离线 Mock 可以证明流程可运行，但不能作为真实模型决策效果的证明；相关材料必须明确标注这一边界。
- DYN-007（P0）：决策依据只记录可审计的简要原因和观察，不记录或提交模型内部思维过程。

## 9. 异常与边界场景

- EXC-001（P0）：缺少 `request_id`、主题、预算或截止时间时，必须指出缺失项并请求补充；主题空白、预算为负或截止时间不是含时区的合法 ISO-8601 时间时，必须明确拒绝；以上情况均保持未完成且不得凭空补值。
- EXC-002（P0）：任一被验收注入的工具失败必须出现在工具结果和步骤状态中；系统须据观察调整或停止，并保留仍有效的成功结果。
- EXC-003（P0）：方案保存失败时，必须返回明确失败和未完成状态，不得返回已保存。
- EXC-004（P0）：初始方案超预算但存在可行替代方案时，必须依据观察重选、重新估算，再保存满足约束的方案。
- EXC-005（P0）：不存在预算内可行方案时，必须按 BR-013 返回未完成及预算缺口，不得保存为已完成方案；预算和时间同时不可行时，两项原因均须返回。
- EXC-006（P0）：方案预计完成时间晚于截止时间时必须调整或明确返回未完成；等于截止时间属于可行边界，不得误判为超时。
- EXC-007（P0）：部分工具成功、部分失败时，必须同时保留两类实际结果，并据依赖关系决定后续动作。
- EXC-008（P0）：相同 `request_id` 和相同输入的重复执行必须返回原结果并标记 `duplicate=true`，跨进程重启后仍不得产生多份等价保存记录。
- EXC-009（P0）：达到执行上限时必须停止并明确报告未完成。
- EXC-010（P0）：真实模型不可用时，可提供离线 Mock 入口，但必须标明运行模式和验证边界，不得混同为真实模型运行。
- EXC-011（P0）：首次素材检索无结果时允许模型调整查询；调整后仍无结果时必须返回未完成及素材不足原因，不得编造素材。
- EXC-012（P0）：相同 `request_id` 携带不同输入时必须返回冲突，不得覆盖原结果或保存新方案。

## 10. 关键验收场景

以下场景描述预期行为，不是实际运行结果。每个 P0 场景均须有后续测试或运行证据追踪。

### AC-001：正常完成（P0）

- **Given** 用户提供包含 `request_id`、非空主题、非负预算和含时区合法截止时间的 JSON，且存在同时满足两项约束的方案，所有必需工具可用。
- **When** 用户通过 CLI 发起一次内容活动方案规划。
- **Then** 系统执行任务计划并据实记录步骤状态与工具结果；当前方案费用合计不超过预算，且任务开始时间加步骤串行总耗时不晚于截止时间；本地 JSON 保存成功后，整体状态为已完成，并返回可核对的保存结果。

### AC-002：缺少预算（P0）

- **Given** 用户输入 JSON 未提供预算。
- **When** 用户发起规划。
- **Then** 系统明确指出预算缺失并请求补充；任务保持未完成；不得自行假定预算或声称已保存完成方案。

### AC-003：缺少截止时间（P0）

- **Given** 用户输入 JSON 未提供截止时间。
- **When** 用户发起规划。
- **Then** 系统明确指出截止时间缺失并请求补充；任务保持未完成；不得自行假定截止时间或声称已保存完成方案。

### AC-004：工具失败与部分成功（P0）

- **Given** 一次执行中至少一个前置或中间步骤已成功，并注入一次非保存类工具失败。
- **When** 系统观察到工具失败。
- **Then** 失败步骤和工具错误被据实记录；模型依据失败调整计划或停止；仍有效的成功结果被保留；依赖未满足步骤不得记为成功；如发生重试，不额外计费；若最终无法完成，必须返回明确未完成原因。

### AC-005：保存失败（P0）

- **Given** 当前方案已满足预算和截止时间且保存前的必需步骤成功，但本地 JSON 保存工具返回失败。
- **When** 系统观察到保存失败。
- **Then** 保存状态必须为失败，整体状态必须为未完成；不得声称已保存或已完成；此前仍有效的成功结果必须保留。

### AC-006：超预算后选择可行替代方案（P0）

- **Given** 初始候选方案的估算费用超过预算，且存在费用满足预算和截止时间的替代方案。
- **When** 模型观察到成本超限。
- **Then** 模型调整计划并选择替代方案；系统重新估算替代方案；历史估算仍保留展示，但最终合计只反映当前选定方案且不超过预算；满足其他完成条件后方可保存。

### AC-007：超预算且无可行方案（P0）

- **Given** 所有已评估候选方案均无法满足预算，继续调整也不能形成可行方案。
- **When** 系统确认不存在预算内可行方案。
- **Then** 系统停止并返回未完成；预算缺口等于最低费用候选方案费用减预算且最小为 0；不得把失败或未完成步骤记为成功，不得声称保存了完成方案；仍有效的成功结果必须保留。

### AC-008：无法满足截止时间（P0）

- **Given** 候选方案的任务开始时间加步骤串行总耗时晚于用户截止时间。
- **When** 系统观察到时间约束不满足。
- **Then** 模型调整方案或明确停止；只有调整后的方案重新满足全部约束时才能完成；否则返回未完成及时间相关原因，不得擅自推迟截止时间。

### AC-009：跨进程重复执行（P0）

- **Given** 一个 `request_id` 和对应输入已有持久化的原处理结果，且进程随后重启。
- **When** 用户使用相同 `request_id` 和相同输入再次执行，系统识别重复请求。
- **Then** 系统返回原结果并标记 `duplicate=true`，不产生新的保存或其他业务副作用；若原结果包含已保存方案，仍只存在一份等价保存记录。

### AC-010：两条真实动态决策路径（P0）

- **Given** 至少两次真实模型运行获得了不同的工具观察结果。
- **When** 模型根据观察选择后续动作。
- **Then** 至少两条运行记录分别包含完整的模型决策、工具执行与观察循环，并呈现因观察不同而产生的动作差异；每条记录包含步骤、工具参数、返回摘要、后续动作和简要决策依据，且不是预设日志或仅自动重试。

### AC-011：达到执行上限（P0）

- **Given** 一次执行持续调整或调用工具并达到配置的步数或调用次数上限。
- **When** 上限被触发。
- **Then** 系统停止继续执行，返回明确的未完成状态和上限原因；不得把达到上限记为成功。

### AC-012：失败步骤续跑（P1，可选）

- **Given** 前次执行存在已成功步骤和失败步骤，且成功结果仍有效。
- **When** 用户对失败任务发起续跑。
- **Then** 系统保留并复用仍有效的成功结果，仅处理失败、未执行或已失效步骤；续跑记录保留前次失败事实，重试不额外计费，最终状态由续跑后的实际结果决定。

### AC-013：离线 Mock 的验证边界（P0，模型不可用时适用）

- **Given** 真实模型不可用，交付提供离线 Mock 入口。
- **When** 评审运行离线模式。
- **Then** 运行入口和结果明确标识为 Mock；材料仅据此声明流程验证，不声明已证明真实模型决策效果；真实模型决策证据与 Mock 证据可明确区分。

### AC-014：缺失或非法输入（P0）

- **Given** 输入 JSON 缺少 `request_id`，或主题空白、预算为负、截止时间格式非法或不含时区。
- **When** 用户提交输入。
- **Then** 系统指出具体缺失或非法字段；缺失项请求补充，非法值明确拒绝；任务保持未完成，不自动修正输入，不保存完成方案。

### AC-015：调整查询后仍无素材（P0）

- **Given** 首次素材检索无结果。
- **When** 模型观察检索结果并调整查询后仍无可用素材。
- **Then** 系统记录查询调整和实际检索结果，返回未完成及素材不足原因；不得编造素材、生成无依据脚本或保存完成方案。

### AC-016：完成时间等于截止时间（P0）

- **Given** 当前方案满足预算，且任务开始时间加步骤串行总耗时恰好等于截止时间。
- **When** 系统评估时间可行性。
- **Then** 时间约束判定为满足，不得误判为超时；其他完成条件均满足时可保存并完成。

### AC-017：预算和时间同时不可行（P0）

- **Given** 候选方案同时超出预算和截止时间，且无法调整出可行方案。
- **When** 系统结束规划。
- **Then** 返回未完成，并同时包含预算和时间两项原因；预算缺口按 BR-013 计算，不得只返回其中一项原因。

### AC-018：相同请求 ID 携带不同输入（P0）

- **Given** 一个 `request_id` 已有原处理结果。
- **When** 用户使用相同 `request_id` 但不同输入再次执行。
- **Then** 系统返回明确冲突；原请求、原结果和原保存方案不被覆盖，不产生新的方案保存副作用。

### AC-019：保存内容可独立核对（P0）

- **Given** 一份方案已成功保存为本地 JSON。
- **When** 评审独立读取该保存内容。
- **Then** 可核对原始输入、当前方案、素材引用、脚本、费用、耗时和保存时间；内容与实际运行结果一致，相同请求及相同方案不会产生第二份等价保存记录。
