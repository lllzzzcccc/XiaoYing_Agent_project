# 内容任务规划 Agent 技术方案

- 阶段：Plan
- 上游规格：`specs/spec.md`
- 配套契约：`specs/contracts.md`
- 任务拆分：`specs/tasks.md`
- 技术栈：Node.js + TypeScript + `@earendil-works/pi-agent-core` + `@earendil-works/pi-ai`
- 运行方式：CLI
- 本文只规定技术方案，不包含实现或测试代码。

## 1. 目标与范围

### 1.1 技术目标

- PLN-001：用 Pi Agent 的真实模型工具调用循环完成素材检索、脚本生成、成本估算和方案保存，满足 DYN-001～004。
- PLN-002：以可持久化的应用运行状态为事实来源，模型文本只作为公开说明，不作为步骤成功、费用或保存状态的判定依据。
- PLN-003：以本地 JSON 和原子文件写入满足跨进程防重复及独立读取，不引入数据库、外部持久化或生产级 Runtime。
- PLN-004：以确定性离线测试覆盖业务规则，以真实模型运行材料证明动态决策；两者分开陈述。
- PLN-005：优先交付 P0 核心链路，失败续跑作为独立 P1 增量，不影响核心验收。

### 1.2 非目标

- 不建设 HTTP 服务、图形界面、多 Agent、分布式锁或生产级会话系统。
- 不接入真实发布、支付、采购或内容平台。
- 不持久化 Pi Provider 凭据，不输出模型内部思维过程。
- 不重新实现 Pi Agent Runtime，也不以固定工作流替代模型决策。

## 2. 技术依据与框架职责

官方资料基线：

- [`@earendil-works/pi-agent-core`](https://www.npmjs.com/package/@earendil-works/pi-agent-core)：`Agent` 提供工具调用循环、顺序工具执行、工具前后钩子、事件订阅和错误工具结果。
- [`@earendil-works/pi-ai`](https://github.com/earendil-works/pi/tree/main/packages/ai)：提供 Provider/Model 注册、环境变量认证、统一流式接口及官方 Faux Provider。

职责分配：

- ARC-001：`pi-agent-core` 负责模型回合、工具选择后的执行、工具结果回传和 Agent 事件；应用不手写假的 ReAct 日志。
- ARC-002：`pi-ai` 负责模型解析、Provider 认证和流式调用；真实模式使用配置的 Provider，离线模式使用官方 Faux Provider。
- ARC-003：应用层负责输入校验、业务工具、依赖约束、费用和时间计算、执行上限、运行状态、Trace、去重及最终结果。
- ARC-004：采用 `Agent` 高层接口，不采用低层 `agentLoop`。选择原因是工具钩子和事件处理更适合维护持久化屏障及一致状态。
- ARC-005：工具执行显式配置为 `sequential`，与 BR-002 的串行耗时口径一致；不得沿用默认并行模式。
- ARC-006：工具参数使用 Pi 支持的 JSON Schema，不为参数定义额外引入 Schema 框架。
- ARC-007：项目初始化时核对 Node.js 引擎要求及两个 Pi 包的兼容版本，随后通过 lockfile 锁定；文档记录实际版本和职责，满足 DEL-005、DAC-008。

## 3. 总体结构

### 3.1 模块边界

- `src/cli/`：CLI 参数、JSON 输入、环境配置、stdout/stderr 和退出码。
- `src/domain/`：请求、候选方案、运行结果、状态迁移、费用与时间规则。
- `src/agent/`：Pi Agent 创建、系统提示、Provider 接入、事件协调和执行上限。
- `src/tools/`：四个业务工具及工具错误、依赖检查和故障注入边界。
- `src/store/`：请求记录、运行状态、保存方案和 Trace 的本地 JSON 读写。
- `src/trace/`：公开决策说明、工具参数、结果摘要和后续动作的审计记录。
- `tests/`：领域契约测试、工具测试、Pi/Faux 集成测试和 CLI 子进程测试。
- `data/`：合成素材及费用/耗时目录，不存放真实业务或凭据。
- `examples/`：评审用输入、实际输出、故障注入配置和实际 Trace。
- `.runtime/`：本地运行状态和保存方案，已由 `.gitignore` 排除，不作为交付证据的唯一副本。

### 3.2 主流程

1. CLI 读取 JSON，校验 `request_id` 和其余输入，保留原始输入。
2. 请求网关计算输入指纹，加载已有请求记录：
   - 相同 ID、相同输入且已有原结果：返回原结果并仅在本次响应中标记 `duplicate=true`；
   - 相同 ID、不同输入：返回冲突，不写原记录、不调用 Agent；
   - 新请求：创建运行状态。
3. Agent 协调器注入原始请求、公开费用/耗时目录和系统规则，由模型选择工具。
4. 工具前钩子检查执行上限、依赖和当前方案有效性；工具执行后保存实际结果、步骤状态及 Trace。
5. 模型观察工具结果后选择查询调整、候选方案重估、脚本生成、保存或停止。预设提示只说明目标和约束，不预设固定动作序列。
6. 最终结果由运行状态派生：只有当前方案可行、依赖结果匹配且保存成功时才为 `completed`，否则为 `incomplete` 并返回全部适用原因。
7. 原结果和 Trace 原子持久化；选定实际材料经脱敏检查后复制到 `examples/` 作为评审证据。

## 4. 关键设计取舍

### 4.1 应用状态与 Pi 消息分离

- DEC-T-001：Pi transcript 只保存本次模型交互；应用 `RunState` 是业务事实来源。模型不能通过最终文本直接写入成功状态、费用或保存路径。
- DEC-T-002：每次工具结束、模型回合结束和最终结束时更新运行状态；失败重试追加新记录，不覆盖旧失败。
- DEC-T-003：不引入 Pi 持久会话后端。P0 只需跨进程读取最终原结果和本地方案，P1 续跑再从公开状态重建上下文。
- 关联：SCP-004、OUT-002～007、BR-005～011、FR-009。

### 4.2 模型决策与确定性护栏分离

- DEC-T-004：模型决定下一动作和候选方案；确定性代码只负责校验、计算、依赖、上限和最终状态。
- DEC-T-005：成本超限、时间超限和无素材都是成功工具观察，不是系统异常；模型必须有机会据此调整。
- DEC-T-006：工具抛出的失败由 Pi 转为错误工具结果并反馈模型；不得把错误文本包装成成功内容。
- DEC-T-007：保存工具只接受 `plan_id`，实际输入、当前方案、脚本和估算均从状态读取，避免模型在保存参数中篡改预算、费用或素材引用。
- DEC-T-008：最终响应由状态确定性生成，模型公开总结可作为补充，但不能覆盖状态结论。
- 关联：FR-003～009、DYN-001～005、BR-001～013。

### 4.3 候选方案与执行步骤分离

- DEC-T-009：`CampaignPlan` 表示交付给运营人员的内容活动方案，其中的步骤引用费用目录并带有业务依赖。
- DEC-T-010：`RunStep` 表示 Agent 实际工具调用，记录运行依赖、尝试次数和实际状态。两者使用不同 ID，不混算耗时或状态。
- DEC-T-011：每个候选方案有 `plan_id` 和 `plan_fingerprint`。同 ID 内容变化时，旧脚本和旧估算保留但标为失效，防止误保存。
- 关联：OUT-001～004、FR-004～007、BR-006～008。

### 4.4 费用与时间计算

- DEC-T-012：费用采用十进制模拟单位运算，初始化时锁定一个小型十进制运算依赖，避免二进制浮点影响预算边界；不引入货币、汇率或真实计费。
- DEC-T-013：最终合计只取当前方案指纹对应的最新成功估算；历史估算全部保留展示，但不参与合计。
- DEC-T-014：无可行方案时，从所有成功估算的候选方案中取最低费用计算 `max(min_cost - budget, 0)`。没有成功估算时不编造缺口，返回工具或输入原因。
- DEC-T-015：预计完成时间为任务 `started_at` 加当前方案全部业务步骤的串行耗时，比较采用 `<= deadline`。重试增加运行步骤历史，但不增加方案费用或业务耗时。
- 关联：BR-001～003、BR-013、AC-006～008、AC-016～017。

### 4.5 本地持久化与防重复

- DEC-T-016：请求记录、保存方案和 Trace 分文件存放；文件名使用 `request_id` 的 SHA-256 摘要，原始 ID 保存在内容中，避免路径注入。
- DEC-T-017：输入指纹使用解析后 JSON 的递归键排序规范形式计算 SHA-256；除校验外不归一化主题或截止时间字符串，因此同 ID 的任何输入值差异都形成冲突。
- DEC-T-018：原结果永久保持 `duplicate=false`；重复响应复制原结果后改为 `duplicate=true`，不回写覆盖原结果。
- DEC-T-019：文件写入采用同目录临时文件加原子重命名；临时文件位于 `.runtime/`。P0 保证顺序跨进程调用，不承诺并发同 ID 的分布式或跨进程锁语义。
- DEC-T-020：保存工具本身也具备等价保存保护；同请求同方案重复保存返回已有引用，不同方案不得覆盖。
- 关联：SCP-007、FR-009、BR-009、BR-012、OUT-005、OUT-009～010。

### 4.6 离线与真实验证分离

- DEC-T-021：离线模式使用 Pi 官方 Faux Provider 的脚本化模型响应驱动同一个 Agent、工具和状态链路，不手写预设 Trace。
- DEC-T-022：所有离线输出和 Trace 标记 `mode=mock`，评估文档只声明流程和契约验证。
- DEC-T-023：至少两条真实 Provider 运行材料标记 `mode=real`，展示不同工具观察引起的不同模型动作；真实运行不作为确定性单元测试的替代。
- 关联：DYN-004～007、DEL-006、DEL-017～019、AC-010、AC-013。

## 5. Agent 与工具协调

### 5.1 系统提示边界

系统提示只包含：

- 用户目标和不可更改的输入约束；
- 四个工具的能力及参数合同；
- 费用/耗时目录的公开元数据；
- 依赖、重估、保存和停止条件；
- 每个动作前输出简短公开 `decision_note` 的要求；
- 不编造素材、不虚报成功、不披露内部思维过程的要求。

提示不得规定“固定依次调用所有工具”的唯一流程，也不得包含预设成本结果或预设决策日志。

### 5.2 工具钩子

- `beforeToolCall`：检查工具上限、当前步骤依赖、方案指纹和保存前置条件；被阻止的调用形成明确失败观察，不执行底层工具。
- 工具 `execute`：执行纯业务动作或抛出带错误码的工具异常；底层故障注入也在此边界发生。
- `afterToolCall`：记录真实参数、成功或错误结果、当前方案变化和运行步骤，随后原子持久化。
- Agent 事件订阅：记录回合和后续动作，限制公开文本，不保存 thinking 内容。
- 达到上限时阻止新工具并终止当前循环，最终由协调器返回 `EXECUTION_LIMIT_REACHED` 和 `incomplete`。

### 5.3 执行上限

- 默认最大实际接受执行的工具调用数为 12，可由非敏感环境配置调整为正整数。
- 计数包含失败工具调用，不包含被参数解析或前置检查阻止且未执行的调用。
- 重试同样计数，防止通过自动重试绕过上限。
- 上限仅是安全护栏，不计为模型动态决策证据。

关联：FR-010、DYN-005、EXC-009、AC-011。

## 6. 数据与保存方案

### 6.1 合成数据

- `data/materials.json`：素材 ID、主题标签、可引用事实和摘要。
- `data/cost-items.json`：费用项 ID、说明、十进制模拟单位费用、秒级耗时。
- 数据不含真实隐私或密钥；修改数据后，工具观察和模型动作应随之变化。

### 6.2 运行文件

- `.runtime/requests/`：原始输入、指纹、运行状态、原结果和保存引用。
- `.runtime/plans/`：可独立读取的最终本地 JSON 方案。
- `.runtime/traces/`：按时间顺序追加的公开审计事件。

保存方案包含原始输入、当前方案、素材引用、脚本、当前费用和耗时明细、任务开始时间、预计完成时间及保存时间，满足 OUT-010 和 AC-019。

### 6.3 评审证据

- `examples/` 保存选定的实际输入、实际输出、故障注入配置和 Trace，而非仅复制预期结果。
- 至少覆盖正常、输入不足和工具失败，并通过更多用例覆盖全部 P0 场景。
- 至少两份真实 Trace 证明动态路径；离线材料单独标识。
- 文档引用相对路径，保证评审能够核对输入、动作、保存文件和最终状态。

## 7. 错误与恢复策略

- 输入缺失或非法：在 Agent 前返回；有效 `request_id` 的新请求仍记录原结果，以支持后续重复与冲突判定。
- 无素材：空列表是正常观察；模型调整查询后仍为空，最终返回 `NO_MATERIALS`。
- 成本或时间不可行：保留每次成功估算；模型可换方案，最终无可行方案时返回全部适用原因。
- 工具失败：保留错误和成功历史；模型可换动作或停止，失败步骤永不变成成功。
- 保存失败：保留脚本和估算，最终不得返回保存引用或完成状态。
- 模型或 Provider 错误：记录 `MODEL_UNAVAILABLE` 或相应模型错误，不用 Mock 结果冒充真实运行成功。
- 进程中断：已持久化步骤保留；无最终结果的运行标记为中断未完成。P1 续跑另行实现，不阻塞 P0。
- 请求冲突：不调用模型和工具，不覆盖任何原始记录。

## 8. 测试与验证策略

### 8.1 测试层次

- 领域契约：JSON 校验、指纹、十进制费用、串行耗时、截止等值、缺口和状态迁移。
- 工具契约：四个工具的参数、依赖、空结果、失败、方案失效和保存等价。
- Agent 集成：使用官方 Faux Provider 验证真实 Pi 工具循环、不同观察后的动作、错误回传、上限和 Trace。
- CLI 集成：通过子进程验证 stdout、退出码、本地文件、跨进程重复和同 ID 冲突。
- 真实运行评估：使用配置的 Provider 生成实际材料，单独记录模型局限和失败。

### 8.2 测试先行规则

- 每个行为任务先写一个会因缺失行为而失败的契约测试，再实现最小行为，最后重构并运行相关测试。
- 禁止先写实现再补一个只验证既有实现的断言。
- 标准离线测试不依赖真实密钥；真实模型验证单独执行并如实记录结果。
- 保存失败和工具失败通过工具边界注入，不伪造运行日志。
- 跨进程测试使用独立临时 `.runtime/` 目录，避免污染开发运行数据。

### 8.3 完成门槛

- TypeScript 构建和离线测试全部通过。
- AC-001～011、AC-013～015、AC-017～019 均有自动化或实际运行证据；AC-016 至少有确定性边界测试。
- AC-012 仅在实现 P1 时声明通过，否则明确列为未完成加分项。
- 至少两条真实动态路径满足 OUT-008、DYN-004 和 DAC-004。
- README、规定文档、依赖锁定、`.env.example` 和证据链接完整。
- 仓库无真实密钥、原始笔试 HTML 或运行垃圾文件。

## 10. 待确认与非阻塞事项

- 没有阻碍开始实现的技术待确认问题。
- Pi 包、Node.js 和十进制运算依赖的准确版本在初始化任务中核对兼容性或可用性并锁定，不在 Plan 阶段虚构。
- 具体 Provider、模型 ID 和提供商凭据通过运行环境选择；应用合同不依赖某一家供应商。
- 同 `request_id` 的并发执行不提供跨进程锁保证，作为本地单机 P0 的已知限制记录；规格要求的顺序跨进程防重复仍必须满足。
- GitHub URL、评审账号和最终 commit SHA 仍按 Q-009 在提交阶段处理。
